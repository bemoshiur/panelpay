# Go-live in one account (WPU-Z11)

Rules: R3 (no long-lived AWS keys; CI uses GitHub OIDC), R12 (every product flag stays off: buying is off at go-live), R16 (fail closed), and the CLAUDE.md rules "never deploy production by hand" and "never touch the management account". Owner decision of 2026-11-13: staging and production live in the SAME member account (the owner's AWS profile `your-aws-profile`), the full platform goes live at `tryaws.now` through the protected CI job, and buying stays off.

What the controller did already (2026-11-13): the SES identity `tryaws.now` is verified; every GitHub environment variable of `staging`, `production` and `production-plan` is set (account, domains `staging.tryaws.now` / `admin-staging.tryaws.now` and `tryaws.now` / `admin.tryaws.now`, admin allowlist, alarm e-mails, `TC_PROBE_SOURCES=198.51.100.1/32` until the NAT address is known, `TC_VPC_CIDR=172.26.0.0/16`, `TC_STAGE_SIZE=lean`, the SES values and the three CI role ARNs of `TcCiDeployStaging`, `TcCiPlanProduction` and `TcCiDeployProduction`); the environment `production` accepts deployments only from tags `v*`.

Isolation in the one account is a policy guard, not an account wall. Each CI deploy role creates and changes IAM roles only under its own stage's names, and is denied what SST tags for the other stage and the other stage's role, function, log, bucket, state, passphrase, parameter, secret, queue, topic, table, database, schedule, alarm, key-alias, budget, CloudFront Function and WAF names. Every role a stage creates carries that stage's permissions boundary (`TcCiRoleBoundaryStaging` or `TcCiRoleBoundaryProduction`) with the same kind of deny. Neither role may change the shared SST bootstrap (`/sst/bootstrap`, the `sst-state-*` and `sst-asset-*` buckets). Known residuals (Needs decision of WPU-Z11): CloudFront distributions, the response headers policy `tc-<stage>-security-headers` and KeyValueStores (id-based ARNs; a KeyValueStore takes no tags; whether CloudFront evaluates the `sst:stage` tag on distributions is a VERIFY), ACM certificates (random ids, tag guard only), the SES identity `tryaws.now` that both stages share (`ses:*`), and the shared SST asset bucket `sst-asset-*`: function code objects have keys without the stage, so either deploy role can overwrite the code the other stage deploys. A staging deploy role can technically reach those of production. Neither deploy role may create or use an S3 access point, so the name-based object denies cannot be bypassed that way. Therefore separate accounts for staging and production remain the stronger option, and the way back is the three-account design of [single-account-lean.md](single-account-lean.md).

## Trigger

The owner decides to put the platform live, or to repeat a step of this page after a change of the CI roles, the secrets or the domains.

## Who

The owner, in their own terminal and on GitHub. A Claude Code session never runs these scripts, never runs `sst secret`, never deploys a stage and never sees a secret value.

## Steps

Each step names the exact command. Run them in order, from the repository folder.

1. **Push main.** The merged work must be on GitHub: `git switch main && git pull --ff-only && git push origin main`.
2. **Load the AWS keys** of the profile into this terminal only (the JOURNEY.md pattern; SST cannot read an `aws login` profile, and nothing may fall back to another profile):

   ```bash
   aws login --profile your-aws-profile
   CREDS="$(aws configure export-credentials --profile your-aws-profile --format env)" && eval "$CREDS"
   export AWS_CONFIG_FILE=/dev/null AWS_SHARED_CREDENTIALS_FILE=/dev/null
   unset AWS_PROFILE CREDS
   aws sts get-caller-identity --query Account --output text
   ```

   The last command must print the account of the platform (a member account, never the management account). Close the terminal at the end of the session; the keys are temporary and never written to a file.

3. **CI roles.** `gh auth status` must show the owner, then run `scripts/golive/ci-roles.sh`. It refuses when the credentials do not work or belong to the management account. It reads the GitHub owner and repository ids with `gh api repos/bemoshiur/panelpay` (GitHub signs the immutable OIDC subject `repo:bemoshiur@<owner id>/tryaws.now@<repo id>:environment:<name>` for this repository; without `gh`, export `TC_GITHUB_OWNER_ID` and `TC_GITHUB_REPO_ID` from `gh api repos/bemoshiur/panelpay --jq '.owner.id,.id'` on another machine). It deploys `infra/org/ci-oidc-provider.yaml` only when `aws iam list-open-id-connect-providers` shows none for `token.actions.githubusercontent.com` (an account holds one provider per URL; the role templates build its ARN themselves), then `tc-ci-deploy-staging`, `tc-ci-plan-production` and `tc-ci-deploy-production`. It prints only stack names and statuses; each must end `CREATE_COMPLETE` or `UPDATE_COMPLETE`. A `FAILED` line: open the stack events in the CloudFormation console, fix by pull request, run the script again.
4. **Pool and DNS roles** (once, if not done yet): follow [single-account-lean.md](single-account-lean.md) "Role stacks in the one account" with `ControlPlaneStage=production`. The pool and DNS roles trust one stage; with `production` the staging functions cannot provision, which is fine because buying is off.
5. **GitHub environment `production`.** Deployments only from tags `v*` (set on 2026-11-13; check it under Settings, Environments). Required reviewers are not available for a private repository on the owner's GitHub plan, so **pushing the `v*` tag IS the approval** of the production deploy: anyone with write access to the repository who pushes a `v*` tag deploys production (the tag commit must be on `main`, and the workflow checks that). The environment `production-plan` has the same `v*` tag policy. GitHub facts (read 2026-11-14, WPU-Y5):
   - The repository is private on GitHub Free. Rulesets are refused there (`gh api` answers HTTP 403, "Upgrade to GitHub Pro or make this repository public"), and so are required reviewers on an environment.
   - The gate today is the deployment tag policy `v*` of the environment `production` (active): only a run from a `v*` tag can deploy production.
   - The repository has one collaborator, the owner, so only the owner can push a `v*` tag. Accepted while that holds.
   - **Before adding any collaborator with write access:** buy GitHub Pro, then run `bash scripts/golive/tag-ruleset.sh` with `gh` logged in as the owner. It creates (or, on a second run, updates in place) the repository ruleset `tc-release-tags`: target tag, `refs/tags/v*`, rules creation, update and deletion, with only the repository admin role (bypass actor `RepositoryRole` id 5) allowed past it. It reads the ruleset back and exits 1 when GitHub holds another form; on HTTP 403 it says GitHub Pro is needed and exits 3 with nothing changed. VERIFY on the first run: the ruleset page lists "Repository admin" as the only bypass and the enforcement is Active. Then add the owner as required reviewer on `production`. Without both, every new collaborator with write access can deploy production.
6. **Secrets of both stages.** `scripts/golive/stage-secrets.sh staging`, then `scripts/golive/stage-secrets.sh production`. Each sets every secret of `infra/lib/functions.ts` (`ALL_SECRETS` and the five database passwords): random values for the internal keys and the database passwords, the Gennet API token through a hidden prompt and the SMS sender id through a visible prompt (both optional: an empty answer sets nothing, the stack's placeholder `not-configured` applies and SMS is off, so the phone OTP says SMS is unavailable and nothing is sent to Gennet; on production that is not allowed unnoticed: the post-deploy check of step 8 fails while the deploy output `smsConfigured` is false, and the alarm `NotifierSmsOffAlarm` fires, see [sms-gateway.md](sms-gateway.md), WPU-Y5), and each EPS value through a hidden prompt where an empty answer stores `not-configured` (the platform then has no EPS: every top-up says "not available" and nothing is sent to EPS). The last prompt, `FirstAdminSub`, stays empty now: leave empty until the Cognito admin exists (step 9.2). A name that already has a value is skipped (on staging `SmsApiKey` and `SmsSenderId` were set on 2026-11-13); `--force` replaces. The production run also writes the SST passphrase `/sst/passphrase/tryaws-now/production` and, together with the staging run, `/sst/bootstrap`, which the read-only plan role needs and cannot write. The bootstrap is shared by both stages and no CI role may change it: after an SST upgrade, run one SST command with administrator credentials (for example `scripts/golive/stage-secrets.sh staging`, which skips the set names) before the next CI deploy, so SST bootstraps again.
7. **Staging test session.**
   1. Start the deploy: `gh workflow run deploy-staging.yml --ref main -f gate=M0`, then `gh run watch`. The job summary shows the `sst diff`.
   2. Smoke checks: `curl -sS -o /dev/null -w '%{http_code}\n' https://staging.tryaws.now/bn` prints `200`; `https://staging.tryaws.now/dev/ui` answers `404`; `https://admin-staging.tryaws.now/` answers from an allowlisted address only; sign up with a test e-mail (the code e-mail arrives from `tryaws.now`) and a test phone (the OTP SMS arrives; with the SMS secrets on the placeholder the phone step says SMS is unavailable instead); the wallet top-up page says top-up is not available (EPS `not-configured`); every product page says it is not open (flags off).
   3. **The two manual proofs of gate M5** (before any tag). `deploy-production.yml` runs `pnpm verify --gate M5`, and that gate holds two checks that only a person can pass: `manual-m5-gate-b-staging-cycles` and `manual-m5-reconciler-staging` (`verify/checks.mjs`, catalogue `verify/manual-proofs.mjs`). Each runs `node scripts/manual-proof.mjs <proof id>` and is BLOCKED (exit 2) until `verify/manual-proofs.json` (today `{}`) holds a valid record for the id, so without these two records the production `verify` job stops and nothing deploys. The gate is never weakened to get past this. Take the evidence while staging runs; record it after.
      - Prerequisites for the session: an admin on `https://admin-staging.tryaws.now/` (step 9.2 works the same on staging), a pool account registered for staging (the migrator path of step 9.3 with the `staging` environment, see [pool-account-single.md](pool-account-single.md)), and the pool and DNS role stacks trusting staging. Step 4 deploys them with `ControlPlaneStage=production`, with which staging cannot provision; for this session deploy both again with `ControlPlaneStage=staging` ([single-account-lean.md](single-account-lean.md), "Role stacks in the one account", and its warning about the DNS roles), and deploy them again with `ControlPlaneStage=production` before the production tag. On the admin `/catalog` page turn on, for this session only, the flags `container_service`, `cdn`, `dns_zone` and `domain` (with their dependencies), and turn every flag off again before removing the stage.
      - Proof `m5-gate-b-staging-cycles` (Lead developer). Needed (catalogue text): "the Gate B adapters (container service, CDN, DNS, domains) pass their cycles on staging" (Section G gate M5; backlog WP7-T1 to WP7-T4). With a test customer whose wallet holds credit, run for each family a create to destroy cycle and watch the operation on the admin `/operations` page: container service (create, deployment running, destroy; no registry login is ever issued), CDN distribution (create, deployed, destroy), DNS zone (create, records added and validated per type, the apex NS and SOA read-only, destroy), domain (search, registration with contact, verification state, renewal state). A domain registration is a real, non-refundable purchase on the platform's AWS bill: register one only with the owner's agreement, and write down which domain and why. Evidence: for each family, the operation ids and their final states (`succeeded` for create and destroy, never `failed` or `needs_attention`), and the date; screenshots or outputs stored with the JOURNEY.md entry of the session. Never an account id, an ARN, a key or a customer's personal data (R3, R14).
      - Proof `m5-reconciler-staging` (DevOps). Needed (catalogue text): "metering ran; the reconciler reports zero unexplained resources and a cost variance under 2% on the latest day Cost Explorer has data for" (Section G gate M5; backlog WP7-T5, WP7-T6; product brief, cost integrity). Let the scheduler run metering and the daily reconciler run once after the cycles (or invoke the two functions of the stage once from the Lambda console). Evidence: the reconciler's log line `reconcile_ok` for the day (no `reconcile_findings` and no `reconcile_incomplete` line), the admin `/reconciliation` page showing no open orphan or missing resource, the metering charges of the day in the ledger, and the cost variance worked out by hand: Cost Explorer daily unblended cost without tax of the latest complete day against the expected cost (hours alive x monthly price / 744 for each live resource, grace hours, retained snapshots and unattached static IPs as their own lines), under 2%. The reconciler code does not compute the variance itself, so the evidence names both figures and the result.
      - Record each proof by pull request to `main` (one record per id, never a guess): add to `verify/manual-proofs.json` a key with the proof id and an object with exactly the three keys the script accepts, `evidence` (at least 20 characters: what was seen and where it is written down, for example the JOURNEY.md entry and the run or ticket), `recordedBy` (the person, at least 2 characters) and `recordedAt` (an ISO 8601 date-time with a zone, for example `2026-11-15T21:05:00+06:00`, not in the future). Any other key, a short text or a missing zone keeps the check BLOCKED. Shape: `{ "m5-gate-b-staging-cycles": { "evidence": "<what was seen, where it is written down>", "recordedBy": "<name>", "recordedAt": "<date-time with zone>" } }`, and the same for `m5-reconciler-staging` in the same object.
      - Check before the tag, on the merged `main`: `node scripts/manual-proof.mjs m5-gate-b-staging-cycles` and `node scripts/manual-proof.mjs m5-reconciler-staging` each print `manual proof <id>: recorded by ...` and exit 0, then `pnpm verify --gate M5` passes. Only then go to step 8.
   4. Remove the stage when the session ends (cost): run the workflow `remove-staging.yml` from the Actions tab (Task 10 adds it), then `gh run watch`. The data stores of staging are retained by the removal policy.
8. **Production.** On `main`, after the staging session passed: `git tag -a v0.1.0 -m "First production deploy"` and `git push origin v0.1.0`. The workflow `deploy-production.yml` runs `verify` (gate M5), `plan` (read-only `sst diff` in the job summary) and `deploy`. Read the plan summary; the pushed tag is the approval (step 5), so stop the run in the Actions tab if the plan shows anything unexpected. `gh run watch` until the post-deploy check ends `PASS`.
9. **After the first production deploy.**
   1. NAT address: in the EC2 console (Region `ap-southeast-1`), read the public IPv4 address of the NAT instance of the production VPC. Put it into the variable `TC_PROBE_SOURCES` of the environment `production` as `<address>/32` (`gh variable set TC_PROBE_SOURCES --env production --body '<address>/32'`) and redeploy with the next tag (`git tag -a v0.1.1 -m "Probe source" && git push origin v0.1.1`). Until then no Linux create can be probed (buying is off anyway).
   2. First admin with TOTP (WPU-Z18; CLI steps, in this exact order; the admin app refuses NEW_PASSWORD_REQUIRED and MFA_SETUP). The admin pool id is the output `adminPoolId` of the deploy job.
      1. Create the Cognito admin without a message: `aws cognito-idp admin-create-user --user-pool-id <adminPoolId> --username <owner e-mail> --message-action SUPPRESS`. Set a permanent password typed at a hidden prompt: `read -rs PW && aws cognito-idp admin-set-user-password --user-pool-id <adminPoolId> --username <owner e-mail> --password "$PW" --permanent; unset PW`.
      2. Enrol TOTP in an authenticated session (`aws cognito-idp associate-software-token` with the session of a password sign-in, the secret into the authenticator app, then `aws cognito-idp verify-software-token`, then `aws cognito-idp admin-set-user-mfa-preference --software-token-mfa-settings Enabled=true,PreferredMfa=true`).
      3. Read its sub (a UUID, not a secret): `aws cognito-idp admin-get-user --user-pool-id <adminPoolId> --username <owner e-mail> --query "UserAttributes[?Name=='sub'].Value" --output text`.
      4. Set the secret `FirstAdminSub`: run `scripts/golive/stage-secrets.sh production` again. Every name that has a value is skipped; at the last prompt ("leave empty until the Cognito admin exists") paste the sub. Compare it with the output of step 3 before you press Enter: a well-formed but wrong sub gives the superadmin row to nobody, and the bootstrap never fires again (stop and write a Needs decision then). The script accepts only the UUID form, stores it in lowercase and prints the name only. Until this step the stack's placeholder `not-configured` stands in for the value, and the migrator writes no admin. If the script reports `skipped FirstAdminSub (already set; --force replaces it)`, never re-run it with `--force` (it rotates every random key and the database passwords); set the one name by hand with `npx sst secret set FirstAdminSub --stage production` (value on standard input, as the Rollback section describes) and redeploy.
      5. Redeploy with the next tag (for example `git tag -a v0.1.2 -m "First admin" && git push origin v0.1.2`). The migrator runs at every deploy, with the master user, inside the private network (R2): when `FirstAdminSub` holds a UUID and `admin_users` has no row at all, it inserts one active `superadmin` row for that sub and one audit row (actor `system`, reason "first superadmin bootstrap"), in one transaction under the advisory lock of `admin_users`. Its log line `migrator_first_admin` says `inserted` and holds at most the first 8 characters of the sub (`skipped: admins exist`, `skipped: no secret` or `skipped: malformed` otherwise). A malformed value writes nothing (the script refuses one, so it can come only from a value set by hand); set the right value and redeploy.
      6. Sign in on `https://admin.tryaws.now/` with the e-mail, the password and the TOTP code.
      7. Then leave the secret as it is: it never fires again, because `admin_users` has a row from now on (every later deploy logs `skipped: admins exist`), even if that admin is later disabled. Removing the value is optional and changes nothing.

      The same order works on staging (`scripts/golive/stage-secrets.sh staging`, then `deploy-staging.yml`). Never open a database path for it (R2), and never write the row by hand.

   3. Pool account (WPU-X4; the database is private, R2, so the CLI `pnpm seed:pool-account` cannot reach it). The migrator registers the one pool account at deploy time when the environment holds exactly one id in `TC_POOL_ACCOUNT_IDS` and the variable `TC_POOL_EXTERNAL_ID`.
      1. Read the ExternalId of the stack made from `infra/org/pool-roles.yaml` in step 4 (a plain value, not a secret, 6.3): `aws cloudformation describe-stacks --stack-name <pool roles stack name> --query "Stacks[0].Parameters[?ParameterKey=='ExternalId'].ParameterValue" --output text`. It shows in the `sst diff` job summary like `TC_DNS_EXTERNAL_ID`; keep it out of chat, tickets and the repository.
      2. Set it as a variable (never a secret) of the environment: `gh variable set TC_POOL_EXTERNAL_ID --env production` (value on standard input). Both deploy workflows pass it to the deploy; only the migrator function receives it.
      3. Redeploy with the next tag (for example `git tag -a v0.1.3 -m "Pool account" && git push origin v0.1.3`).
      4. Check the log of the migrator function (CloudWatch, the Lambda `migrator` of the stage): the line `migrator_pool_account` says `inserted` with `cellsCreated` 26 and `accountSuffix` (the last 4 digits only). Every later deploy says `skipped: exists` and changes nothing; limits and `used` are never overwritten. `skipped: not configured` means the variable is empty, `skipped: several pool accounts` means more than one id (use [pool-account-single.md](pool-account-single.md) and the admin path instead), `skipped: malformed` means the value does not match the pattern of `pool-roles.yaml` (fix it and redeploy). `skipped: differs` means a row for this account exists with another name, tier or ExternalId, or the alias `pool-1` belongs to another account; nothing was written and the deploy went on. Correct the variable, or empty it when the account was registered another way. Only a database error fails the deploy (`migrator: could not register the pool account`). A step that wrote something also wrote one `audit_log` row (actor `system`, reason "pool account bootstrap") in the same transaction.
      5. On `/capacity` of the admin app set each limit to the recorded real quota (audited, R10): the migrator writes the seed's low placeholder limits.

      The same steps work on staging (`gh variable set TC_POOL_EXTERNAL_ID --env staging`, then `deploy-staging.yml`).

   4. Launch data (WPU-X8, found on the first staging deploy of 2026-11-14: a stage without the market BD refuses every sign-up). Nothing to do by hand: at every deploy the migrator runs `seedLaunchData` of `packages/db/seed/launch.ts` as the master user, right after the migrations and before the ledger accounts, in one transaction. It inserts only what is missing and never changes a row that exists (an edited price, limit or flag stays), so a second deploy writes nothing.
      - Production (`TC_STAGE` = `production`): the market BD in BDT with the top-up limits the owner decided on 2026-11-14 (minimum 100 BDT, maximum 50,000 BDT per payment, no quick amounts, active), the market pricing rule, the config prices (snapshot, unattached static IP, DNS zone with its price book), the single-admin adjustment limit of 10,000 BDT of WPU-X5 (with one `audit_log` row, actor `system`) and the twelve feature flags, every one off (R12). **No FX rate** is written.
      - Staging (`TC_STAGE` exactly `staging`): the same, plus the test FX rate 127 (only when the market has no rate at all) and the flags `linux_instance`, `static_ip`, `backup` and `disk` on. A missing or unknown `TC_STAGE` is treated as production (fail closed: never the test rate or flags that are on).
      - Check the log of the migrator function: one line `migrator_launch_seed` with `environment`, `market`, `fxRate`, `pricingRule` (true when this deploy inserted it) and `flagsAdded` (a count). The first deploy says `market: true` and `flagsAdded: 12`; every later deploy says false and 0. A failure stops the deploy with `migrator: could not seed the launch data` and writes nothing (one transaction; the later steps do not run).
      - The first FX rate in production: the seed writes none, so every price, purchase, draft and renewal is refused (`prices_updating`) until an admin saves the first rate on `/pricing`. One admin (`finance` or `superadmin`) sets the first rate of the market alone and it is in force at once (WPU-X9, owner decision 2026-11-14). Later changes of up to 3% within 24 hours (from every rate in force in that time; a re-confirm of the same rate included) are also set by one admin alone; only a larger change, or a change before a rate that is already scheduled, needs a second, **different**, active `finance` or `superadmin` admin to approve it (WPU-Y1). A rate is fresh for 7 days only (`FX_RATE_MAX_AGE_DAYS`): after that pricing refuses again until a new rate (or the same rate again) is saved. The same holds on staging 7 days after the seeded rate 127. See [fx-rate-change.md](fx-rate-change.md).
   5. Set the first FX rate on `/pricing` (step 4) before buying opens. Second admin: a change of more than 3% within 24 hours needs four eyes (two different admins), so the superadmin invites a second person on `/admins` (role finance or superadmin) before such a change is needed.
   6. Leave every product flag off. Buying stays off until the owner decides otherwise (R12).
   7. Budget: confirm each alarm e-mail subscription (Amazon SNS sends a confirmation message) and the next day read the cost in Cost Explorer. While `TC_BUDGET_ALARM` is `off` (an organization SCP denies budgets to this account, 2026-11-14), the stage has no budget of its own: **before buying opens**, the owner creates the budgets in the management account ([single-account-lean.md](single-account-lean.md), "When an organization SCP denies budgets"). Without them production cost is not watched. With the switch `on`, check instead that the stage budget and its e-mails exist in AWS Budgets.

## Rollback

- A production deploy that fails part way: SST leaves the previous resources in place; fix by pull request and push the next tag. To return to the last good version, push a new tag on the last good commit (`git tag -a v0.1.2 <good commit> -m "Rollback"` then `git push origin v0.1.2`); the tag must be on `main`.
- A broken staging: run `remove-staging.yml`, fix, run `deploy-staging.yml` again.
- A wrong secret: run `scripts/golive/stage-secrets.sh <stage> --force` (every value is replaced; the random keys change, so customer sessions and drafts expire) or set the one name with `npx sst secret set <Name> --stage <stage>` by hand, then redeploy.
- A wrong CI role stack: fix the template by pull request and run `scripts/golive/ci-roles.sh` again; never delete the Deny statements of a CI role.

## What to log

In JOURNEY.md: the date of each step, the stack names and statuses of step 3, the names (never the values) of the secrets set in step 6, the tag pushed, the result of the post-deploy check, the NAT address change, and every VERIFY result (the OIDC subject in the first AssumeRoleWithWebIdentity event of CloudTrail, any AccessDenied of a CI role).

## Must not

- Never run these steps from a Claude Code session, and never paste a secret value, an account id or an ARN into a chat, an issue or this page.
- Never deploy production by hand. `infra/lib/stage.ts` refuses the stage production unless `CI=true` and `TC_PRODUCTION_DEPLOY=ci-approved` are set; that guard stops mistakes, not a person who sets the two variables. `scripts/golive/stage-secrets.sh` sets them only for its own `sst secret list` and `sst secret set` calls (a ruling is requested), and refuses any other sst command.
- Never use the management account; `scripts/golive/ci-roles.sh` refuses it.
- Never widen a CI role by removing a Deny statement; widen by pull request after reading the AccessDenied in CloudTrail.
- Never turn a product flag on at go-live.
